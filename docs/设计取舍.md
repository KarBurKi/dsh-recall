# 设计取舍

这份文档记录 dsh-recall 为什么长这样，以及**刻意不做**的东西。判断依据来自对
[dsh-meow-memory](https://github.com/Phant0Meow/dsh-meow-memory)（MIT）的源码、文档与
B 站讲解视频（BV18Ubv6tEWN）的阅读，以及其评论区 300+ 条真实反馈的归纳。

## 出发点

meow-memory 把「记忆」当成一个独立子系统来做：七层模型、8 个工具、SQLite、
首轮整块注入、每消息关键词命中、反思、夜间 dream、UI 折叠、设置页。功能完整，代价是：

1. **固定开销**：8 个工具 schema 实测约 2,464 tok，另有一份 1,988 tok 的 system prompt 手册，
   合计约 4,452 tok/请求——这还没算每轮注入。
2. **每轮成本**：首轮整块注入动态记忆，之后每条消息 top-2 命中。
3. **后台成本**：反思与 dream 都是真金白银的 API 调用。
4. **耦合风险**：注册核心服务后，与计费类插件重复注册会导致 host 起不来（评论区多例）。

自己用的时候，第 2、3 条是纯消耗：记忆是否"相关"由关键词打分决定，模型自己判断往往更准。

## 于是砍掉

| 砍掉 | 理由 |
|---|---|
| 首轮整块注入 | 内容随工作区变化，等于每个新会话重付一次；且挤占上下文 |
| 每消息 top-2 命中 | 每轮都付，是评论区「污染上下文」的主要来源 |
| 反思（连续 7 step 后询问） | 与任务无关的额外模型调用；用户实测算过账 |
| 夜间 dream / 峰时抑制 / 中断自愈 | 一整套后台状态机，是兼容性 bug 的高发区 |
| 8 → 3 个工具 | `find_similar`/`read`/`update`/`dream`/`home` 在日常使用中极少触发 |
| 客户端 UI（折叠、图标、设置页） | 需要 client 半 + 轮询/SSE，纯成本，不影响记忆本身 |

## 保留

- **稳定前缀**：只往 AGENTS.md 加一段固定文本（106 tok），不碰 system prompt 的动态部分。
- **按工作区隔离**：scope 默认取 `exec.agent.session.header.cwd` 的目录名，不需要模型传参。
- **关键词检索 + 时间衰减**：中文 bigram + ASCII 词，BM25（k1=1.4, b=0.72），半衰期 60 天。
  宁可召回略宽，也不要"越搜越偏"。
- **近乎重复合并**：重叠系数 ≥ 0.9 才合并（只防手抖重写），语义重复交给 `mem_find` 后人工判断。

## 结构选择

- **JSONL 而非 SQLite**：`node:sqlite` 在 Node 22.5–22.12 需要 flag，宿主的 Node 版本不可控；
  纯文本可直接读、改、diff、拷走，符合「数据即文件」。
- **零运行时依赖**：不 import 任何 `@deepseek-ai/*` 包（以 `link:` 装入时解析不到）。
- **不注册核心服务**：只 `ctx.tools.register`，热重载由 `ctx.effect` 的 dispose 负责。

## 已知局限

- 没有语义检索（embedding），同义改写要靠 bigram 兜底 + 人写的 `keywords` 补。
- 模型必须"想起来"调用 `mem_find`；没有自动注入，冷启动依赖 AGENTS.md 那一行指引。
- 没有跨会话的自动整理；记忆多了需要人（或模型）主动 `mem_forget`。
- 单文件 append 写入，多进程同时写不保证顺序；实际并发极低，暂不处理。

## 关键词为什么让人写，不自动提取（0.2.0）

v0.1.0 只用正文 bigram 做 BM25。实测栽在改写上：库里写「配置越精简越好」，
查询「配置要精简」的分词交集只有「配置」「精简」两对，打分被长句稀释，排到后面。

试过自动提取（TF-IDF 取高权重 bigram 当关键词）——没用，因为**它只是正文的子集**，
给子集加权等于把同一批词重复计分，改写依旧不命中。

所以改成写入时由模型给 2–5 个**同义词/别名/缩写/英文写法**。这不是提取，是翻译：
`离线` ↔ `offline`、`转写` ↔ `ASR` ↔ `whisper`，正文里完全没有的词也能命中。
代价是 `mem_save` 多一个参数、模型每次多想一步；换来的是召回。

打分改成字段化 BM25（正文 ×1、关键词 ×1.8、目标句 ×1.4），关键词原文整串出现在查询里再 +0.9。
关键词参数也做了兜底：不写就按旧逻辑走，返回里会明说「没给关键词（以后检索会弱一些）」，不静默降级。

## 从 memory-eternal 学到的三条（0.3.0）

B 站 BV1iGnA6WEAR 推的是 [memory-eternal](https://github.com/EternalNight996/memory-eternal)。
拆完它那份 133KB 的 README，只有三条值得搬；其余（每轮 LLM 蒸馏、审核门、常驻 web、
看门狗、知识图谱）都是为「后台自动跑」付的复杂度税，我们不在后台跑，就不交。

**一、跨库召回。** 它的卖点是「跨项目提问自动召回」，本质就是多个库一起查。
改成 `mem_find` 默认同时读当前工作区与 `global`，两个库**各算各的 BM25** 再合并
——混在一起算 avgdl 会让小库被大库带偏。来自 `global` 的结果标 `〔global〕`，让模型知道来源。

**二、写入闸门。** 它的「捕获最小长度 200」，以及 v0.10.23 那张「注入垃圾卡」清单
（技能目录行、`<system-reminder>` 碎片被当成用户消息存了）。我们手动存很难踩，
但一旦开始批量补记就会踩。加两条：正文 < 12 字拒收（12 这个数是因为 15 字的完整句子
在测试里被 16 字闸门误杀过一次），`- \`` 或 `#` 开头的清单行/标题行拒收。

**三、物理隔离 → 改口提醒。** 它 v0.10 把未审核内容挪进另一张表，理由是 v0.9 审计
**实测漏过三处**：去重池往待审卡里追加、`readCard` 按 path 直读未审正文、`/card` 无状态校验。
这条「不要依赖每处代码都记得过滤」的思路值得学，但我们没有自动写入源，审核门是空转。
所以只取「读路径必须安全」这半条，落地成**改口提醒**：关键词撞上两个以上、正文又不像、
两边都带数字（端口/版本/路径这类）时，在返回里提示可能与旧卡冲突，**只提醒不自动作废**。

它自己还踩过一个更值钱的坑：相似度 0.93 的两张卡结论可能**互相矛盾**，盲合并会把冲突
悄悄"和解"掉、还永久删掉源卡。我们的合并阈值 0.9 正落在这个危险区间——所以合并只防手抖重写，
冲突一律交给人判断。

## 从 dsh-agent-soul 学的一条（0.3.1）

B 站 BV12jn66jEyD 推的是 [dsh-agent-soul](https://github.com/cyanwell/dsh-agent-soul)。它本身不存记忆，
是一套架构说明书 + 体检表（8 个工具、约 4–5K tok 常驻）。整套东西里只有一条直接打中了我们：

**索引必须带回原文的指针。** 它的 ECHO 架构说得很直白：摘要一旦不带出处，就从「索引」变成了
「第二份真相」——而且是一份会被压缩、会被转述、会随时间变形的真相。账本纪律也写着：一条没有出处的
`fact`，三个月后读到只能选择相信或不信，而两条路都不对。

我们的卡片正是这种摘要。0.3.0 之前，一条记忆写完就只剩下「我整理的那句话」，半年后无法核对。

所以 0.3.1 在写入时自动记 `s`（当前会话 uuid），`mem_find` 显示成 `〔s:xxxxxxxx〕`。
顺着它回到 `~/.dsh/sessions/--<工作区>--/session-<uuid>/session.v4.jsonl.zstd`。

刻意没做的：

- **不存全文** —— 那就不是索引了，是两本账。
- **不存消息序号** —— 会话日志是 zstd 压缩流，序号不可靠；uuid + 时间戳足够定位到那次会话。
- **不强制** —— 取不到 session id（旧版/测试桩）就留空，并在返回里明说「回溯不了原文」，不编造。

它还有三条判据值得记住（不落成代码，落成规矩）：唯一权威源（两处都写 = 双重记账）、
每条阈值防的是哪一次具体的失败、局部规矩必须写清适用范围。

## 以后可能加

- `/dream` 之类的显式整理入口（成本另算，不默认跑）。
- 可选的 embedding 检索（需要用户自备服务，默认关闭）。
- 按 scope 的导出/导入（目前拷 `.jsonl` 即可）。

## 实测

| 项 | 数值 |
|---|---|
| 3 个工具 schema | 620 tok（o200k_base） |
| AGENTS.md 指引 | 106 tok |
| 固定开销合计 | **≈ 726 tok/请求** |
| 对照：meow-memory 0.31 | 约 4,452 tok/请求（未计每轮注入） |
| 对照：memory-eternal 0.10 | README 自带省钱包四道闸（蒸馏开关/输出上限/捕获长度/日配额），默认就是会烧钱的 |
| 写入 / 检索延迟 | 本地文件 + 内存 BM25，毫秒级 |
| v0.1.0 → v0.2.0 增量 | +176 tok（keywords + goal 两个参数） |
| v0.2.1 → v0.3.0 增量 | +49 tok（只有 `mem_find` 说明变长；跨库、闸门、提醒都是行为不是接口） |
| v0.3.0 → v0.3.1 增量 | +3 tok（`mem_save` 多一个可选输出字段 `ref`；记出处是行为不是接口） |

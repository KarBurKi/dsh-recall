# 设计取舍

这份文档记录 dsh-recall 为什么长这样，以及**刻意不做**的东西。判断依据来自对
[dsh-meow-memory](https://github.com/Phant0Meow/dsh-meow-memory)（MIT）的源码、文档与
B 站讲解视频（BV18Ubv6tEWN）的阅读，以及其评论区 300+ 条真实反馈的归纳。

## 出发点

meow-memory 把「记忆」当成一个独立子系统来做：七层模型、8 个工具、SQLite、
首轮整块注入、每消息关键词命中、反思、夜间 dream、UI 折叠、设置页。功能完整，代价是：

1. **固定开销**：8 个工具 schema 实测约 2,464 tok，另有一份 1,988 tok 的 system prompt 手册，
   合计约 4,452 tok/请求——这还没算每轮注入。
2. **每轮成本**：首轮整块注入动态记忆，之后每条消息 top-2 命中。
3. **后台成本**：反思与 dream 都是真金白银的 API 调用。
4. **耦合风险**：注册核心服务后，与计费类插件重复注册会导致 host 起不来（评论区多例）。

自己用的时候，第 2、3 条是纯消耗：记忆是否"相关"由关键词打分决定，模型自己判断往往更准。

## 于是砍掉

| 砍掉 | 理由 |
|---|---|
| 首轮整块注入 | 内容随工作区变化，等于每个新会话重付一次；且挤占上下文 |
| 每消息 top-2 命中 | 每轮都付，是评论区「污染上下文」的主要来源 |
| 反思（连续 7 step 后询问） | 与任务无关的额外模型调用；用户实测算过账 |
| 夜间 dream / 峰时抑制 / 中断自愈 | 一整套后台状态机，是兼容性 bug 的高发区 |
| 8 → 3 个工具 | `find_similar`/`read`/`update`/`dream`/`home` 在日常使用中极少触发 |
| 客户端 UI（折叠、图标、设置页） | 需要 client 半 + 轮询/SSE，纯成本，不影响记忆本身 |

## 保留

- **稳定前缀**：只往 AGENTS.md 加一段固定文本（75 tok），不碰 system prompt 的动态部分。
- **按工作区隔离**：scope 默认取 `exec.agent.session.cwd` 的目录名，不需要模型传参。
- **关键词检索 + 时间衰减**：中文 bigram + ASCII 词，BM25（k1=1.4, b=0.72），半衰期 60 天。
  宁可召回略宽，也不要"越搜越偏"。
- **近乎重复合并**：重叠系数 ≥ 0.9 才合并（只防手抖重写），语义重复交给 `mem_find` 后人工判断。

## 结构选择

- **JSONL 而非 SQLite**：`node:sqlite` 在 Node 22.5–22.12 需要 flag，宿主的 Node 版本不可控；
  纯文本可直接读、改、diff、拷走，符合「数据即文件」。
- **零运行时依赖**：不 import 任何 `@deepseek-ai/*` 包（以 `link:` 装入时解析不到）。
- **不注册核心服务**：只 `ctx.tools.register`，热重载由 `ctx.effect` 的 dispose 负责。

## 已知局限

- 没有语义检索（embedding），同义改写要靠 bigram 兜底。
- 模型必须"想起来"调用 `mem_find`；没有自动注入，冷启动依赖 AGENTS.md 那一行指引。
- 没有跨会话的自动整理；记忆多了需要人（或模型）主动 `mem_forget`。
- 单文件 append 写入，多进程同时写不保证顺序；实际并发极低，暂不处理。

## 以后可能加

- `/dream` 之类的显式整理入口（成本另算，不默认跑）。
- 可选的 embedding 检索（需要用户自备服务，默认关闭）。
- 按 scope 的导出/导入（目前拷 `.jsonl` 即可）。

## 实测

| 项 | 数值 |
|---|---|
| 3 个工具 schema | 426 tok（o200k_base） |
| AGENTS.md 指引 | 75 tok |
| 固定开销合计 | **≈ 501 tok/请求** |
| 对照：meow-memory 0.31 | 约 4,452 tok/请求（未计每轮注入） |
| 写入 / 检索延迟 | 本地文件 + 内存 BM25，毫秒级 |
